Tutorial

A guided tour of Crisp. Early steps cover everyday syntax. Steps 11–16 are the advanced stretch: methods, traits, shapes, generics, Rust crates, and async. Each step starts with a beginner intro, then a short snippet, then what happens under the hood.

Before you start Follow Install until crisp run examples/hello prints "hello world". You need Rust 1.85+ and cargo install crisp-lang.
Step 01

Hello world

Start here. A Crisp program is a few items in a .crp file. You define work with name(args) = …, bind locals with :=, and mark the process entry as pub main.

You do not need to understand every line on the first pass. This example already uses a shape, a defaulted struct, string interpolation, and an implicit generic id. Treat those as “names you will meet again”; the goal now is to run something.

shape Named = {
    name: str
}

type Guest = {
    name: str = "world"
}

id(x: T) = x

greet(who: Named) = "hello {who.name}"

pub main() = {
    world := Guest {}
    print(id(greet(world)))
}
  • shape Named is structural: any type with name: str can be greeted.
  • Guest {} fills the default name = "world". Interpolation writes "hello {who.name}".
  • id(x: T) is an implicit generic — unbound T is a type parameter. <> is only a pin.
  • No semicolons; the last expression in a block is the value (here print returns unit).

Try: crisp run examples/hello

Under the hood: crisp analyzes the crate, emits a normal Cargo project under target/rust/, then cargo run. rustc remains the soundness boundary — if emitted Rust fails to compile, that is treated as a compiler bug, not a user debt.

Step 02

Functions and bindings

Most Crisp looks like small math and logging. A function is name(args) = body. Inside a block, x := value creates a local; later x = … assigns only if the binding was introduced with mut:= (see loops).

If you know JavaScript const / let, think := as “introduce” and = as “update.” If you know Python, there is no silent rebind of an immutable name — mutability is marked.

double(n) = n + n

pub main() = {
    x := double(5)
    log("x={x}")
}
  • pub exports the item from the module (needed for main and for other files to use it).
  • print / log both write to stdout; prefer log when interpolating.
  • Omit types while the shape of the program is clear; add them when APIs should be stable.

Under the hood: HM-style type inference plus a separate ownership pass. Silence means “infer”; an annotation is a hard constraint the solver must satisfy.

Step 03

Strings and comments

Text is the str type. Line comments are --; block comments are nested {- … -}. A string can interpolate an expression: "hello {name}".

++ concatenates two strings. Interpolation is usually clearer when you mix text and values. Quotes in the snippet below are ordinary string literals, not a special template language.

-- single-line comment
{- block comment -}

greet(name: str) = "hello " ++ name

pub main() = {
    who := "world"
    log("greet={greet(who)}")
}
  • "{expr}" interpolates — here the call greet(who) is evaluated inside the string.
  • You can annotate early (name: str) to document an API even when inference would succeed.

Under the hood: Interpolation lowers toward Rust format!-style formatting in the emitted project. String values are owned String (or borrowed where the ownership pass proves it safe).

Step 04

Types when you need them

Inference is the default, not a limitation. You can leave parameters untyped while a function is used in one obvious way. Annotate when two interpretations are possible, when you design a public boundary, or when you want the compiler to reject a silent mix-up.

Beginners often annotate too early or never. A practical rule: skip types in a 10-line script; write them on anything other files will use. Primitives below are the everyday set.

port(host: str, n: int) = n
  • Common primitives: int, uint, float, bool, char, str.
  • Return types can be written -> T on functions when you want them explicit.

Under the hood: int/uint/float map to Rust i64/u64/f64 in the current bootstrap. Annotations feed the same constraint solver as inferred uses — they are not a second type system.

Step 05

Structs and defaults

A type Name = { … } is a record: named fields grouped under one type. Field defaults mean callers only pass what they care about — typical for config.

This is not a class. There is no inheritance here. Behavior comes later via impl (methods) or trait (shared contracts). For now, think “a bag of fields you construct with Name { … }.”

type ServerConfig = {
    host: str  = "127.0.0.1"
    port: uint = 9000
    debug: bool = false
}

pub main() = {
    cfg := ServerConfig { port: 3000 }
    log("port={cfg.port}")
}
  • Omitted fields fill from defaults (host and debug above).
  • Read fields with cfg.port — same idea as other systems languages.
  • If field access on a parameter is ambiguous across several structs, annotate the parameter (see limitations).

Under the hood: Struct types become Rust structs; defaults are applied at construction in the emit layer. Field projection participates in ownership inference (& vs owned) like other places.

Step 06

Modules

One .crp file under src/ is one module. Mark helpers pub and import them with use module { item } — similar in spirit to Rust modules or TypeScript imports, with lighter syntax.

You do not write mod foo; in source. The compiler discovers files from the crate layout (crisp.toml + src/). Start with a flat src/main.crp and one extra file; nested folders come when the project grows.

-- src/arith.crp
pub sum(a, b) = a + b

-- src/main.crp
use arith { sum }

pub main() = {
    log("sum={sum(2, 3)}")
}
  • Flat src/*.crp modules can import each other without worrying about file order.
  • Nested paths such as src/math/vector.crp become a nested Rust module tree when emitted.

Under the hood: Resolve builds a module graph from the crate root (crisp.toml + src/). Visibility and use are checked before typeck; emit then writes a conventional mod tree for Cargo.

Step 07

Tests

Write checks next to the code. test "…" is a positive assertion: run the body and fail the test if an assert_eq does not hold. test_compile_fail expects analysis to reject the body — “this must not typecheck.”

Run them with crisp test . from the crate root (several paths are allowed). Keep cases small and named. Compile-fail tests are how the language suite guards diagnostics; they are also useful in your own crate when a mistake should stay illegal.

test "greet works" = {
    assert_eq(greet("world"), "hello world")
}

test_compile_fail "unknown name" = {
    definitely_not_a_builtin()
}
crisp test .
  • Keep tests in the same crate as the code under exercise unless you outgrow that.
  • Prefer small named cases over one giant script.

Under the hood: Positive tests become Rust #[test] functions in the emitted crate. Compile-fail tests are run by the Crisp harness (expect diagnostics), not by hoping rustc fails on bad user code.

Step 08

Fallible functions

When a function can fail, mark it with ambient !. Use throw to fail and catch to recover. You can think “this returns a value or an error” without writing Rust Result by hand.

This is not exception unwinding across unknown frames in the Java sense. The ! is part of the function’s type: callers must handle failure or themselves be fallible. catch is the local recovery point. See examples/fallible before inventing a large error hierarchy.

parse_port(s) ! = {
    if s == "" then throw "empty"
    -- …
}

pub main() = {
    p := parse_port("8080") catch { e => 0 }
    log("port={p}")
}
  • ! on the function means callers must handle failure (or themselves be fallible).
  • catch { e => … } turns an error into a normal value at that site.
  • See examples/fallible for chaining and richer error sets.

Under the hood: Ambient errors lower to Result<T, CrispError> (and related plumbing) in emitted Rust. The error pass tracks which error variants a function may produce; sealed crates freeze those signatures at publish time.

Step 09

Enums and match

An enum names a closed set of cases: a plain tag (Red) or a tag with payload (Custom(int, int, int)). match is how you branch on every case. If you know Rust enums or TypeScript discriminated unions, this will feel familiar.

Prefer an enum when a value is “one of these,” not a boolean plus extra fields. Construct and match with a qualified name: Color.Red. Exhaustiveness means if you add a variant later, matches that forgot it should fail to compile.

type Color =
    | Red
    | Green
    | Blue
    | Custom(int, int, int)

describe(color) = match color {
    Color.Red -> "red"
    Color.Green -> "green"
    Color.Blue -> "blue"
    Color.Custom(r, g, b) -> "rgb({r},{g},{b})"
}
  • Write variants as Color.Red when constructing or matching.
  • Payloads bind names in the arm (r, g, b above).

Try: crisp run examples/enums

Under the hood: Enums become Rust enums; match becomes a Rust match. Exhaustiveness is enforced in analysis so emit does not rely on “hope the arms cover it.”

Step 10

Loops

Crisp has three loop forms. while repeats while a condition holds. for x in xs walks a vec (MVP). loop repeats until break; break expr can give the whole loop a value. Counters that change need mut:=.

There is no C-style for (i = 0; i < n; i++). Use while plus a mutable counter, or put values in a vec and for. continue skips to the next iteration. Labels and enumerate are not there yet — see limitations.

sum_to(n) = {
    total mut:= 0
    i mut:= 0
    while i < n {
        i = i + 1
        total = total + i
    }
    total
}

countdown_stop(start, stop) = {
    n mut:= start
    loop {
        if n == stop then break n
        if n <= 0 then break 0
        n = n - 1
    }
}
  • mut:= introduces a mutable binding; later updates use plain =.
  • break expr exits a loop with a value — the whole loop expression yields that value.
  • for MVP iterates Crisp vec; richer iterators are still growing (see limitations).

Try: crisp test examples/loops

Under the hood: Loops lower to Rust while / loop / for with mutable locals. Parser disables struct-literal greed in if/while/for heads (Rust-style) so while i < n { … } parses cleanly.

Step 11

Inherent methods

So far, functions have been free-standing: double(n), greet(who). An inherent method belongs to one type. You write impl Type = { … }, then call Type.new(…) for constructors and value.method() for operations on an instance.

Use this when the operation only makes sense for that type — magnitude of a Vec2, not of an arbitrary pair of numbers. self is the receiver (the value before the dot). You do not write self: Vec2; the impl already names the type. This is not yet a trait: nothing else can “implement Vec2 methods.” Shared behavior across types is the next step.

type Vec2 = {
    x: float
    y: float
}

impl Vec2 = {
    pub new(x: float, y: float) = Vec2 {
        x: x
        y: y
    }
    pub magnitude(self) =
        (self.x ** 2.0 + self.y ** 2.0) ** 0.5
}

pub main() = {
    v := Vec2.new(3.0, 4.0)
    log("mag={v.magnitude()}")
}
  • ** is exponentiation (lowers to a float power call).
  • Call associated items as Vec2.new(…); call methods as v.magnitude().

See also: examples/vec2_methods

Under the hood: Inherent methods become Rust impl Type { … }. Receiver mode (&self vs owned) is chosen by the ownership pass from how self is used.

Step 12

Traits

A trait is a named contract: “this type can show itself as text.” You declare the operations, then write an explicit impl Trait for Type for each type that should participate. Several types can share the same trait; one type can implement several traits.

Contrast with the previous step. Inherent impl Point is “functions that live on Point only.” impl Show for Point is “Point agrees to the Show protocol,” so other code can ask for “anything that can show.” The prelude also offers Show / Eq / Ord-style helpers for everyday types.

From v1.6.1, if a generic function calls a unique trait method — label(x: T) = x.show() — the compiler infers T: Show from the body. You keep parametric T; a call with a type that has no impl Show is a typeck error (E0084). You still write the impl for each concrete type. Written where clauses, generic trait bounds, and dyn Trait are not the stable path yet.

trait Show = { show(self) -> str }

type Point = {
    x: int
    y: int
}

impl Show for Point = {
    show(self) = "({self.x},{self.y})"
}

label(x: T) = x.show()

pub main() = {
    p := Point { x: 1, y: 2 }
    log("p={p.show()} l={label(p)}")
}
  • Prefer traits when several types share a behavior you want to name.
  • label(x: T) = x.show() infers T: Show from the body (v1.6.1 / #84). Written where / generic trait bounds / dyn Trait are still limited — see limitations and examples/trait_defaults.

Try: crisp test examples/show_trait

Under the hood: Traits lower toward Rust traits / impls. A unique method on generic T records a nullary bound and typeck E0084 rejects instantiations without an impl. Full Rust-style written bounds / dyn Trait remain partial.

Step 13

Shapes

A shape is a structural requirement on fields: “anything with x and y floats.” Matching structs do not need an explicit impl. If the fields are there with the right types, the value already satisfies the shape.

Think of this as a typed form of “duck typing” for data, not for methods. A trait says “this type promised a named protocol.” A shape says “this value has these fields.” Use a shape when many records share a layout (points, vectors, cells) and you do not want each one to implement a trait. Use a trait when the interesting part is behavior (show, minus) rather than field names.

The snippet below is the concrete, float-only form (examples/shapes). The next step makes the same idea parametric: HasPosition<T> works for int and float because + - * infer numeric bounds.

shape HasPosition = {
    x: float
    y: float
}

type Point = {
    x: float
    y: float
}

distance(a: HasPosition, b: HasPosition) -> float = {
    dx := a.x - b.x
    dy := a.y - b.y
    dx * dx + dy * dy
}

pub main() = {
    p := Point { x: 0.0, y: 0.0 }
    q := Point { x: 3.0, y: 4.0 }
    log("d={distance(p, q)}")
}
  • Use a shape for “duck” field requirements; use a trait for named behavior.
  • Point satisfies HasPosition automatically because the fields match.
  • Parametric HasPosition<T> (next step) infers T: Add / Sub / Mul from + - * — examples/shapes_generic.

Try: crisp run examples/shapes · also examples/shapes_generic

Under the hood: Shapes lower to a generated Rust trait plus accessors so emit stays coherent. Method/anonymous shape edges are still limited — prefer named data shapes as in the example.

Step 14

Generics

A generic item is written once and used at many types. id(x: T) = x works for int, str, or a struct — T is a placeholder filled in at each call. Prefer implicit binders: an unbound name in type position is already a parameter. Write <> only to pin a definition or to apply arguments: Pair<int, str>, Boxy<int>.

If you know Java or C# <T>, the idea is the same, but Crisp usually omits the angle brackets on the definition. type Pair = { left: A, right: B } is already generic in A and B. A name that is already a type (int, Pair) stays that type; it does not become a parameter.

Keep parametric T. If the body uses + or x.show(), the compiler infers the constraint (T: Add, T: Show) instead of secretly specializing to one concrete type. A bad instantiation is a typeck error (E0084), not only a later rustc failure. User types with user methods (not int +) live in examples/shapes_user.

type Pair = { left: A, right: B }

id(x: T) = x
first(p: Pair<A, B>) = p.left

shape Boxy = { value: T }
unwrap_int(b: Boxy<int>) = b.value

pub main() = {
    p := Pair { left: 1, right: 2 }
    log("id={id(41)} first={first(p)}")
}

Keep that rule in the second snippet: HasPosition<T> is still a shape; the numeric bound sits on distance, inferred from - and *.

shape HasPosition = { x: T, y: T }

distance(a: HasPosition<T>, b: HasPosition<T>) = {
    dx := a.x - b.x
    dy := a.y - b.y
    dx * dx + dy * dy
}
  • Free names (T, A, B) become parameters. <T> is a pin — same meaning, optional.
  • A matching struct satisfies Boxy<int> automatically; no impl required for the shape.
  • + - * on T infer Add / Sub / Mul. Unique methods infer a trait bound (x.show() → T: Show). User methods on a user type: examples/shapes_user.
  • Written where / generic trait bounds / dyn Trait are still limited — see limitations.

Try: crisp test examples/generics_implicit · also examples/generics, examples/shapes_generic, examples/shapes_user, examples/generics_pub

Under the hood: Implicit params stay rigid in the definition and instantiate at call sites. Shapes emit trait Boxy<T> plus structural impl Boxy<i64> for IntBox. Arith on T emits std::ops; typeck checks the bound before rustc. Field access on a type parameter currently requires T: Clone in the generated Rust. pub schemes freeze in crisp.lock.

Step 15

Import a Rust crate

Crisp is a front end that emits ordinary Rust. It does not replace crates.io. When you need JSON, HTTP, or any other Rust library, declare it in crisp.toml with rust = true, then use crate { items } much like importing a package in TypeScript.

Without rust = true, a Cargo dependency is not a Crisp import. The explicit flag is how the compiler knows to forward the crate into the generated Cargo.toml and to resolve use serde_json { … }. Prefer the bare use serde_json { from_str, to_string } form; use rust.serde_json { … } is the explicit alias if a Crisp module shares the name.

Unknown APIs are opaque stubs — you can mention them, but Crisp will not invent their types. Known Result-returning APIs (for example in serde_json / ureq) can surface as Crisp ambient errors (? / catch). Start with examples/rust_import before wrapping a large crate.

-- crisp.toml
-- [dependencies]
-- serde_json = { version = "1", rust = true }

use serde_json { from_str, to_string }

pub main() = {
    v := from_str("[1, true, \"crisp\"]")
    print(to_string(v))
}
  • Compat path: use rust.serde_json { … } if you prefer an explicit namespace.
  • Known Result-returning APIs can surface as Crisp ambient errors (? / catch) — see limitations.

Try: crisp run examples/rust_import

Under the hood: Dependencies with rust = true are forwarded into the emitted Cargo.toml. Crisp does not reimplement those crates — it generates ordinary Rust uses against them.

Step 16

Async

Mark main or a block async when work must wait (timers, I/O) without you writing threads by hand. await suspends until a future is ready. Start with a tiny sleep_ms to prove the runtime is wired; then look at spawn/join in the examples.

This is the same idea as JavaScript async / await or Rust Tokio: the function can pause and the runtime can run other work. It is not a second Crisp scheduler. The bootstrap emits a Tokio-oriented Cargo project when the crate is async. Closures as first-class values (passing an async callback around) are still v1.7.0 — keep examples small.

pub main() = async {
    sleep_ms(1)
    print("async-ok")
}
  • You still write Crisp — the bootstrap selects a Tokio-oriented emit for async crates.
  • Prefer the examples before inventing large async graphs by hand.

Try: crisp run examples/async_hello · also examples/async_spawn

Under the hood: Async lowers toward Tokio in the emitted Cargo project (runtime = "tokio" in manifests). This is a Rust-hosted async story, not a separate Crisp scheduler.

Step 17

Where to go

You now have the core surface: values, modules, tests, errors, data, then the advanced stretch (methods, traits, shapes, generics, Rust interop, async). Next, read for depth or scan for fit.

If a snippet surprised you, run it from the repo examples first, then change one line. reveal types / reveal rust on the same path shows what silence meant. Honest gaps vs the draft spec live on the limitations page — the compiler is a Rust-hosted bootstrap, not self-hosted yet.
